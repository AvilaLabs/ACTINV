# ACTINV P23 Amendment A — G3 damage-control corpus substitution

**Date:** 2026-09-10. **Trigger:** the frozen G3 clause "`build-damage` controls use a small named
TENDL-2025 subset, hash-pinned in the control" was falsified by a pre-implementation survey of the
workstation nuclear-data store. This amendment records the corrected corpus plan. It does not change
the feature contract, the failure semantics, the tolerance, or any identity rule of the frozen
protocol (`fa0df3411e7e2d1d8c5777810db03e76563d6dec1f695fb9219dc0ce7ee59dd5`).

## Diagnosis

The frozen text assumed TENDL-2025 neutron evaluations carry MF=3/MT=444 damage-energy production
sections. Survey on 2026-09-10 found **zero** files with MT=444 in:

- `~/nuclear-data/tendl-2025/files/n/` — full directory scan, 0 hits (spot files n-Fe056, n-Co059,
  n-Ni058 all carry 62–63 MF=3 sections, none 444);
- `~/nuclear-data/tendl-2025/files/n-working/` — 0 hits;
- `~/nuclear-data/tendl-2023/ci_fe/` — 0 hits;
- `~/nuclear-data/endfb-viii.0-n-test/` — 0 hits;
- `~/nuclear-data/eaf-2010/files/` — the local EAF-2010 subset carries activation MF=3 only (0 hits);
- `~/nuclear-data/alara-2.9.2/data/` — no damage-energy content;
- `~/nuclear-data/fendl-3.2c/` — NJOY input decks do not request MT=444; the GENDF output is flux
  weighting data, not damage-energy production.

Damage-energy production in ENDF-6 evaluations is normally generated by processing codes
(NJOY `heatr`, FISPACT print-outs) rather than distributed as MF=3/MT=444 tabulation; the local
stores confirm that convention.

## Corrected G3 corpus plan

`build-damage` remains exactly as frozen: it collapses every MF=3/MT=444 section it is given through
the same parse → temperature-check → lethargy-collapse path as `build-library`, records every source
file's SHA-256, names every evaluation lacking MT=444 in `uncovered`, and never fabricates or
zero-fills a target. What changes is only the control's corpus:

1. **Synthetic mini-corpus (primary evidence).** The control writes small, well-formed ENDF-6
   evaluations containing declared MF=3/MT=444 sections (covering at least INT=2 and INT=5
   interpolation laws), hash-pins them into the evidence, runs the production `actinv build-damage`,
   and independently re-collapses the same sections — its own per-law lethargy integrator, no
   production code — comparing every group value at the frozen `1e-9` relative bound. The corpus also
   contains an evaluation without MT=444 so the `uncovered` ledger entry is exercised on the same run.
2. **Real-data honesty leg.** The control also runs `build-damage` over a small named real
   TENDL-2025 subset (hash-pinned file list) and verifies the produced table has an empty `targets`
   map, an `uncovered` list naming every input evaluation, and complete per-file SHA-256 provenance —
   demonstrating the tool reports rather than invents on a real directory.
3. All other G3 battery legs (mono-group closed form, independent fold, ledger honesty,
   mesh/single-cell agreement, Python parity, identity) are unchanged and use synthetic
   `actinv-damage-table-1` tables whose bytes and SHA-256 are recorded in evidence.

## Why this is honest

The feature under test — collapse MF=3/MT=444 and fold to NRT dpa — is identical whether the ENDF
section was written by an evaluator or by the control. The synthetic sections exercise the same
parser, the same interpolation laws, and the same collapse routine; the independent re-collapse is
genuinely independent (it shares no code path). The real-data leg preserves the frozen intent that
the builder face a real evaluation directory and tell the truth about coverage.

A caveat now explicit in the ledger/docs (G4): until a damage table derived from a distributed
MT=444 source or an NJOY-computed damage-energy source is available, `build-damage` on TENDL-2025
produces an empty `targets` map — users must supply NJOY `heatr`-processed or equivalent ENDF files.
This limitation is documented rather than hidden.
